SERIAL DIAGNOSTICS · VERSION 1.3

Serial Link Tester

Measure integrity, throughput and timing across a serial connection, in one direction or both at once.

Your first test

  1. Open SerialLinkTester.exe. Use Try demo to explore the interface without hardware. Demo mode never opens a COM port.
  2. Connect your serial adapter and install its Windows driver if needed. Close terminal programs that are using the test ports. Select Refresh ports.
  3. Two ports / bidirectional is selected by default. Select different Port A and Port B on the same PC and connect both TX/RX paths. Choose Two ports / one way if you only need one direction.
  4. Match the baud rate and electrical interface at both ends. The application uses 8 data bits, no parity, 1 stop bit, flow control off.
  5. Default settings are Latency and jitter, a 64-byte payload, 60 seconds and a 1000 ms (1 second) response threshold / final receive window. Increase the receive window for slow links or larger packets as needed; serialization time is included. Then use Integrity and throughput at 50%, 90% and 100% target load. The target includes protocol overhead; actual load depends on the host and driver.
  6. Select Start test. When the duration expires or you select Stop, the receiver remains open for the final receive window.
  7. Choose Export report after completion. A dated subfolder contains a readable HTML report, packet-level CSV and JSON summary.

Choose a connection

Transmit COM port → Device or link under test → Receive COM port

The binary test stream must pass through unchanged. Both ports are on the same PC, so timestamps share a clock. With both paths wired, swap the port selections to test the reverse direction on its own.

Two ports / bidirectional: select Port A and Port B. Each port sends and receives at the same time. Both streams have independent session IDs, sequence numbers and results.

A TX → Local device → Link → Remote device → B RX
B TX → Remote device → Link → Local device → A RX

Connect both TX and RX paths at each endpoint and remove any remote loopback. The adapters, wiring and tested link must support simultaneous traffic. This mode does not implement half-duplex bus arbitration or two-wire RS-485 direction control.

The baud rate, payload, duration and timeout apply to both directions. In throughput mode, target load applies to each direction independently: 100% requests full target load A to B and full target load B to A. In latency mode, each direction waits for its own packet before sending another probe; a timeout in one direction does not stall the other.

The overview shows both directions together. Select A → B or B → A to view that direction's metric cards, chart and details. The Missing column shows Pending during the run. Serial warnings are observations from shared physical ports and cannot be attributed exclusively to one direction.

Export produces a comparison report, a combined CSV with a direction column, and a JSON summary of both directions. The A_to_B and B_to_A subfolders contain individual reports. Combined CSV rows are grouped by direction; start-relative timestamps use each direction's own start. Stop ends both senders and preserves the final receive windows. A port I/O failure aborts the session and marks incomplete directions.

One port / round trip: return the remote serial TX output to its RX input with suitable wiring. The response returns to the same PC port. This measures round-trip time; dividing by two does not establish one-way delay.

Baseline: first connect the same adapters with a direct cable or local loopback. Then add the device or link under test, keeping settings unchanged. A baseline characterizes the host path but cannot remove variable buffering from every sample.

Use wiring appropriate to the electrical interface. RS-232, RS-422 and RS-485 are not electrically interchangeable. The application does not implement manual direction control for adapters that require it.

Read the results

MetricMeaning
Pending / missingWhile running, sent packets without an identifiable response are pending. After the final receive window closes, these become missing packets. Missing packets at the end of the stream are included.
CorruptionInvalid payload CRC/pattern or framing events. An unreadable header can count as both an invalid frame and a missing packet; do not add these counts. This is not raw physical-layer bit error rate.
GoodputVerified payload bits per second, excluding protocol overhead. The live value covers the latest sample interval. The final active average covers the first-to-last valid reception interval and needs two valid packets. A whole-session average is listed separately.
LatencyTime from write submission to reception of a complete valid frame, using a single PC clock. Includes the OS, adapter, serialization and device/link buffering.
JitterMean absolute difference between consecutive valid packet delays in receive order. Latency standard deviation is reported separately in Details.
Median / p95 / p99Latency percentiles, using the upper edges of 0.1 ms histogram bins. Resolution is not a physical timing accuracy claim. Values at or above 60 seconds use an overflow indication.
Serial warningsNamed Framing, Break, Overrun, RX overflow and Parity observations, shown in amber. These events do not stop the test. Counts describe observations, not affected bytes. Unknown flags retain their hexadecimal code.
Test-stopping errorsShown separately in red, with the failure message. Failed port opening, read/write failures or an aborted/incomplete test belong here. Serial warnings remain visible independently if both occur.

Serial warnings are cumulative history for the current test. A cable reconnection does not erase earlier observations; a new test resets them. The warning strip does not claim that the line is still faulty. UART Framing warnings are separate from packet-format errors in the Corruption card.

Details also shows duplicates, out-of-order and late packets, unrelated sessions, total wire bytes and the maximum observed driver queue sizes.

Latency in throughput mode is measured under load. It includes queueing and is different from an idle-link latency measurement. A completed write is not a hardware timestamp.

Serial adapter settings

FIFO, transmit completion and buffering options depend on the adapter and its driver. The application does not change vendor-specific settings. Record the adapter, driver version, FIFO options and connection conditions in Test notes.

Compare driver settings using a direct cable. Evaluate dropped data and overruns as well as timing. Do not reduce buffering blindly: a smaller buffer can increase loss. The test does not repeatedly purge receive or transmit queues.

The baud box accepts listed or custom numeric values from 1200 to 1000000. Support and actual baud accuracy depend on both endpoints; verify any nonstandard rate with your hardware documentation.

Limits and requirements

Windows 10/11, .NET Framework 4.x and the driver for your adapter. No application installation or administrator launch is required. Payload: 1–2048 bytes. Duration: 1–3600 seconds. Receive window: 100–60000 ms. Session limit: one million packet records per direction.

This version uses one PC and does not synchronize separate PCs. It tests a transparent binary path or loopback, rather than acting as a general terminal. Demo results are simulated and clearly labeled. Automated tests do not replace physical hardware validation.
